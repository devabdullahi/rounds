# Condition profile schema (draft 0.1)

One profile per condition: the reusable medical knowledge that cases are built from. An LLM generates it once, in stages. Then code validates it, a second model reviews it, and a clinician approves it. Profiles name the diagnosis, so like everything in `knowledge-base/` they never reach the patient LLM.

- `condition_profile.schema.json`: the JSON Schema (draft 2020-12)
- `examples/acute-appendicitis.json`: the reference example given to the generator

## Principles

1. **Each fact appears once.** Repeating a fact across sections invites contradictions, so derived views are built by code.
2. **IDs, not free text.** Labs use `reference_ranges.json` test ids. Clerkships and organ systems use the app's enum raw values. Differentials link to other profiles by `slug`. Exam findings can carry a SNOMED id later.
3. **The model describes, code computes.** The model gives value ranges per severity, in our units. Code picks the patient's actual numbers, computes derived labs and scores, and enforces lab math.
4. **Paraphrase criteria.** Never quote copyrighted criteria (e.g. DSM-5) verbatim.

## Generation stages

Each stage is one LLM call, validated before the next one runs.

| Stage | Fills | Runs on |
|---|---|---|
| 0 `triage` | `triage` | All 707 conditions (cheap) |
| 1 `patient_presentation` | `patient`, `presentation` | Case-suitable conditions only |
| 2 `exam_vitals` | `exam`, `vitals` | 〃 |
| 3 `diagnostics` | `labs`, `ecg`, `imaging`, `workup` | 〃 |
| 4 `differential_course` | `differential`, `course`, `cancer` | 〃 |
| 5 `teaching` | `teaching` | 〃 |

## Derived by code (not generated)

| Thing | Built from |
|---|---|
| Case-generation rules (must / may / avoid) | `almost_always` items → must; `common`/`sometimes` → may; `pertinent_negatives` + `argues_against` → avoid |
| Grading rubric | `teaching.key_questions` + `exam.findings[].importance` + `workup` + must-not-miss differentials + `accepted_names` |
| Key exam maneuvers | `exam.findings` with `importance` essential/important |
| Expected-findings summary | `strongly_supports` exam findings, `essential` labs, confirmatory imaging |
| Lab relationships | The rules engine (anion gap, osmolality, Hgb/Hct, acid–base…), using formulas from `reference_ranges.json` |
| Clinical scores | A shared, hand-checked score library; profiles only list ids in `workup.scores` |

## Rule checks (beyond the schema)

- Every `labs[].test_id` exists in `reference_ranges.json` and isn't a derived test.
- Each range has min ≤ max. A high-direction lab stays at or above the normal low, and the reverse for low-direction labs.
- Vitals use the reference units (°F, not °C).
- Workup tests resolve to a panel or test id, or name an imaging study.
- Differential `slug`s point to existing profiles, or are flagged for later.
- `workup.scores` ids exist in the score library.
- Female-only conditions have `sex: female_only`, and the age range fits the primary clerkship (e.g. pediatrics).

## Feeding cases

At case creation, code picks a profile and samples a severity, patient and presentation from it, then writes `private.case_content`:
- `facts`: from `presentation`
- `exam`: from `exam.findings`
- `tests`: from labs and imaging, with values generated by code
- `answer_key`: from `teaching` and the differential
